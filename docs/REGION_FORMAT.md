# Lanternmere region format

Lanternmere does not use Tiled — it uses the brief's other sanctioned option: "a documented data-driven loader." This document is that documentation, covering the JSON schema `RegionLoader` (`src/Lanternmere.Core/Content/RegionLoader.cs`) reads and validates, and the C# model it deserializes into (`src/Lanternmere.Core/Content/RegionDescriptor.cs`).

## Why not Tiled

A Tiled (.tmx) importer adds a real dependency (either a maintained third-party MonoGame.Extended-style importer or writing one from scratch) for a five-region prototype. The brief explicitly allows a documented data-driven loader as an equal alternative, and a plain JSON format that maps 1:1 onto typed C# records is easier to validate, generate, and unit-test than an XML tile format — see `RegionLoaderTests.cs` and `ShippedContentTests.cs` for what that buys.

## Authoring content

Don't hand-edit the JSON files under `src/Lanternmere/Content/Data/`. They're generated by `tools/ContentGen` (`dotnet run --project tools/ContentGen -- src/Lanternmere/Content/Data`), which builds `RegionDescriptor`/`DialogueTree`/`ItemDefinition`/`DiscoveryDefinition` objects directly in C#, self-validates with `RegionLoader.Validate` before writing anything, and fails loudly (non-zero exit, printed issues) rather than writing invalid content. This guarantees the shipped JSON is always schema-correct and cross-referenced correctly (transition destinations exist, dialogue trees NPCs reference exist, no duplicate ids) — see `Program.cs` for the full generation logic and the specific layout of each region.

To change region content: edit `tools/ContentGen/Program.cs` and re-run it. To add a new field to the format: add it to `RegionDescriptor.cs` (or the relevant sub-type), update the generator if content needs to set it, and it will round-trip automatically since both sides use the same C# types and `System.Text.Json`.

## Schema reference

A region JSON file (`Content/Data/maps/<id>.json`) has these top-level fields:

| Field | Type | Notes |
|---|---|---|
| `id` | string | Must match the filename (by convention; not enforced) and be unique across all regions |
| `displayName` | string | Shown in the region label HUD text |
| `widthTiles` / `heightTiles` | int | Tile grid dimensions |
| `tileSize` | int | Pixels per tile (20 across all current regions) |
| `groundColorHex` / `accentColorHex` | string (RRGGBB, no `#`) | Base colors `TextureFactory` generates ground/wall tile textures from |
| `solidTiles` | int[] | Row-major, length `widthTiles * heightTiles`. Non-zero = collidable. Out-of-bounds tiles are always treated as solid by `RegionDescriptor.IsSolidAtTile` |
| `spawnPoints` | `{ name: {x, y} }` | Pixel-space spawn positions. **Must include a `"default"` entry** — `RegionLoader.Validate` fails without one |
| `interactables` | `InteractableDef[]` | See below |
| `npcs` | `NpcPlacementDef[]` | See below |
| `transitions` | `TransitionDef[]` | See below |
| `ambienceId` / `musicId` | string? | Keys into `AudioLibrary` (`src/Lanternmere/Systems/AudioLibrary.cs`) |

### Interactables

One shape covers landmarks, item pickups, puzzle pieces, and flat examine-text props — the brief asks for a single context-sensitive interaction, not per-type handlers. Key fields: `id` (unique within the region), `x`/`y`/`width`/`height` (pixel bounds), `prompt` (context prompt text), and then any combination of `examineText`, `dialogueId`, `discoveryId`, `grantsItemId`, `setsFlagOnInteract`, `requiresFlag`/`hiddenAfterFlag` (visibility gating), `isLandmark` (counts toward the brief's 8 major landmarks and shows in the journal/map), `isOptionalSecret`, and `puzzleId`/`puzzlePieceIndex` (routes the interaction to a `Lanternmere.Core.Puzzles` controller instead of the generic examine flow — see `RegionScene.InteractWithPuzzlePiece`).

### NPCs

`id`, `displayName`, `x`/`y`, `dialogueId` (a dialogue tree id from `Content/Data/dialogue/`), and optionally `dialogueIdAfterFlag`/`dialogueAfterFlagName` to swap to a different tree once a flag is set (used sparingly — most NPCs instead handle repeat-visit variation inside a single tree via `DialogueCondition`+`FallbackNext`, see `docs/PUZZLES.md` sibling doc `NARRATIVE_BIBLE.md`).

### Transitions

`id`, pixel bounds, `destinationRegionId` + `destinationSpawnId` (both validated to exist), and optionally `requiresFlag`/`lockedMessage` for a gated transition (e.g. the village hub's archive hatch, locked until the player has the brass key) — walking into a locked transition shows the message rather than silently doing nothing or teleporting anyway.

## Validation

`RegionLoader.Validate(Dictionary<string, RegionDescriptor>)` checks, across the whole loaded set at once (so cross-region references can be checked):

- every region has a `"default"` spawn point
- `solidTiles.Length == widthTiles * heightTiles`
- no duplicate ids among a region's interactables + NPCs + transitions
- every transition's destination region and spawn point actually exist
- no interactable sits on a solid tile with all four neighbors also solid (a cheap, sound reachability proxy that catches the common authoring mistake of placing a trigger inside a wall — not a full pathfinding reachability check, which the brief flags as "where feasible")

This runs three times in practice: inside `tools/ContentGen` before writing any file, in `GameContent.TryLoad` at game startup (routing to `MissingContentScene` on failure instead of crashing or running with broken data), and in `ShippedContentTests.AllShippedRegions_PassValidation` against the actual shipped files as part of `dotnet test`.
